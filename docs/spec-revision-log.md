### 7.3 补丁轮中的设计选择（供复核）

最小修法留给设计者的具体选择如下，都已写进规格，列在这里供主管复核：

1. **D1**：回滚后清除在途记录失败时，用进程内的在途登记兜底，没有引入新的记录状态。
2. **D3**：创建即归入 `held` 用新迁移 T22 表达，没有把 T6 的起点扩展到「新建」。
3. **D4**：需要强制清退时结局一律为 `failed`（`protocol_violation`），原候选为 `completed` 也是如此：端点或其后代在 `run.finished` 之后仍可能改动工作区，最终提交不能当作正常完成的结果。退出期限沿用 R §9.6 原有的 10 秒，SIGTERM 到 SIGKILL 的间隔沿用停止升级中的 5 秒。
4. **D4**：`awaiting_input` 收尾期间到达的停止请求采用「提交并排队，返回 `202`」，没有采用让客户端稍后重试的 `409`。
5. **D5**：预算判定一律先于候选。runner 已正常完成、但最终回执首次暴露超限时，run 转 `paused` 而不是 `done`，恢复要先调高预算再 `continue resume`（新建 run 收尾）。这保证「超限必暂停」，代价是已完成的工作要经新 run 才能交付。
6. **D5**：向预算已用尽的任务追加 run 以 `BUDGET_EXHAUSTED` 拒绝（与 `continue` 一致），没有采用「创建后立即转 `paused`」。作废的消息不自动转给续做的新 run。
7. **D6**：阶段之外的操作与字段用新错误码 `501 not_implemented` 拒绝，不写入幂等记录；没有复用 `422 validation_failed`，因为请求本身合法、只是实例还没实现。阶段划分严格对齐计划 §6，依赖与优先级、预算与 `max_steps`、审查与台账不再属于 Phase 1，Phase 1 的范围比 v0.2 返工轮的划分更小。
8. **D7**：`release-worktree` 响应中的 `release.state` 固定为意图提交时的 `pending`。v0.2 条文允许返回 `completed`，但响应必须与释放意图在同一事务中记录，此时删除还没有执行，所以去掉了这一情形；完成与中止都经 run 资源和 `run.updated` 表达。
9. **D8**：固定 SHA 的下游采用「整项跳过」，没有采用「只保留固定 SHA 字段、改写其余字段」，避免依赖新 run、却审查旧 SHA 的混合状态。
